# Wiki conventions

The rules every wiki reader and writer follows. Other skills cite sections of this file by name
(`skills/pavilio-wiki/CONVENTIONS.md § Reading ladder`); keep the headings stable.

## Layout

```
projects/<p>/
├── CONTEXT.md                 # strict glossary: one line per term + See [[wiki/concepts/<term>]]
└── wiki/
    ├── .gitignore             # .ingest.lock*, raw/repos/
    ├── log.md                 # append-only: ingest/query entries + the ledger
    ├── .ingest.lock           # transient, never committed
    ├── raw/                   # raw layer: verbatim snapshots of outside material
    │   └── repos/<owner>-<repo>/   # shallow clones, never committed
    ├── index.md               # GENERATED — sections only, one line each
    ├── overview.md
    ├── sources/               # one source page per record: <kind>-<stem>.md
    ├── entities/              # kind: person | repository | service | organization
    ├── concepts/              # domain knowledge; never names files or functions
    ├── repos/<repo>/          # code subtree: ARCHITECTURE.md + code-level notes
    ├── questions/             # one page per explicit query
    ├── notes/                 # synthesised answers worth keeping
    └── open-questions.md      # ## Gaps, ## Knowledge candidates
```

Every `index.md` (root, each section, each `repos/<repo>/`) is generated by `scripts/wiki index`.
Never edit one by hand; regenerate it.

## Identity and the ledger

- **Record** — a closed workspace file: `notes/**`, `memo/**`, past-day `progress/*.md`, `adr/**`,
  an archived change's `proposal.md` / `design.md`. Never `tasks.md`, delta specs, or today's
  progress. Records are cited in place by their project-relative path, never copied.
- **Raw file** — anything without a stable workspace home, snapshotted verbatim under `wiki/raw/`:
  `<slug>.md` (outside file), `article-<slug>.md`, `youtube-<id>.md`,
  `snippet-<YYYY-MM-DD>-<slug>.md`, `context-snapshot-<YYYY-MM-DD>.md`, its per-section split
  `context-snapshot-<YYYY-MM-DD>/<nn>-<section-slug>.md` (written by migrate; source page
  `sources/context-snapshot-<YYYY-MM-DD>-<section-slug>.md`), `repos/<owner>-<repo>/`. A raw file
  is never rewritten (clones are refreshed in place by `clone-repo`).
- **Source page** — `wiki/sources/<kind>-<stem>.md`, one per record or raw file. `<kind>` is
  `note`, `memo`, `progress`, `adr`, `proposal`, `design`, `file`, `article`, `youtube`,
  `snippet` or `context`; `<stem>` is the file stem with a leading `<kind>-` stripped (the change
  id for `proposal`/`design`), so raw `article-edge-tts.md` → `sources/article-edge-tts.md`, never
  `article-article-…`. On a stem collision append the parent directory name. A changed record
  rewrites its existing source page.
- **Slug** — lowercase kebab-case ASCII; people `first-last`. Frontmatter lists carry bare names
  (`concepts: [utterance]`); receipts, `mentions --touched` and page writers use the namespaced
  form `entities/<name>` / `concepts/<name>`, whose page is `wiki/<slug>.md`. Reuse an existing
  slug or alias before coining one.
- **Ledger** — `- ingested: <project-relative path> #<sha256 first 12 hex>` lines in `wiki/log.md`,
  appended only by `scripts/wiki record`, and only after the record's source page landed. A path
  whose latest hash matches is done; a different hash is `changed`; no line is pending. `pending`
  also lists top-level `wiki/raw/*.md` snapshots on the same terms (never sub-dirs, never the
  migration's `context-snapshot-*.md`, which only migrate takes via `--only`). Repo clones
  are tracked by `commit` in their repo pages, not by the ledger.
- **Lock** — `wiki/.ingest.lock` (`{session, ts}`) via `scripts/wiki lock`; one ingest per wiki;
  older than 15 min is taken over.

## Two sources, and the glossary exemption

A knowledge page (`entities/`, `concepts/`) is written only when ≥2 distinct source-like pages
name its slug. Source-like = `sources/**` and `repos/<repo>/**`; `questions/` and `notes/` never
count. A term `CONTEXT.md` links as `See [[wiki/concepts/<slug>]]` qualifies with one source.
The `knowledge` project is the exception: it has no source pages, its pages are written only by
the knowledge harvest, and the user's pick is the promotion (`SKILL.md § 5. Knowledge harvest`).
`scripts/wiki mentions` counts; never create a knowledge page `scripts/wiki backlog` does not list
under `create`.

`scripts/wiki backlog` turns that rule into the page writers' work list, read from the pages
themselves: `create` — qualifying slugs with no page yet, with every source page naming them;
`update` — existing pages with the source pages their `sources:` does not cite yet; `waiting` —
named but not qualifying. A page writer that never finished leaves its sources in `update`, so the
next run picks them up; a page with an empty backlog is up to date.

## Write regimes

| Path | Writer | Regime |
|---|---|---|
| `raw/` | ingest, `fetch-article`, `fetch-youtube`, `clone-repo` | written once; clones refreshed |
| `sources/` | `source_writer` | one per record; rewritten when its hash changes |
| `entities/`, `concepts/` | `page_writer` | incremental rewrite from the existing page + new source pages only |
| `repos/<repo>/` | `repo_writer` | `ARCHITECTURE.md` rewritten on clone refresh; notes added |
| `overview.md` | `overview_writer` | rewritten when knowledge pages change |
| `index.md` files | `scripts/wiki index` | generated |
| `questions/` | query | one new page per explicit query; never edited after |
| `notes/` | query | new, or enriched in place |
| `open-questions.md` | query, ingest, harvest | append items; people resolve and delete them |
| `log.md` | query, ingest, harvest, `scripts/wiki record` | append-only |
| `sources/` `## Knowledge` | `scripts/wiki backlink` | harvest; ingest re-adds after a rewrite |
| `knowledge/wiki/` `entities/`, `concepts/` | `page_writer`, knowledge-wiki mode | harvest only |
| `CONTEXT.md` | archive-plan, migrate | never this skill |

The harvest also clears the candidates it handled, indented sub-lines included, from each `open-questions.md`
(`scripts/wiki clear-candidates`); a failed page writer's items stay for the next harvest.

People may edit any page. Writers keep `created` and human-added `aliases`.

## Links

One syntax (D14): `[[<path from project root>]]`, no `.md`, optional `<project>:` prefix and
`|label` suffix.

- `[[wiki/concepts/utterance]]`, `[[wiki/entities/jane-doe|Jane]]`
- `[[progress/2026-10-19-tts-relay-node20]]`, `[[adr/0020-agent-memory-is-an-llm-wiki-context-is-a-glossary]]`
- `[[plans/openspec/specs/speech/spec]]`
- `[[metro:wiki/entities/jane-doe]]` — another project

Never relative paths (`../`), never markdown links to workspace files, never a bare slug
(`[[utterance]]`). Every claim on a knowledge page cites the source page it came from. A
`<project>:` link resolves under `projects/<p>/`, then `projects/archived/<p>/`, so it survives
archiving.

These are the links *inside* wiki pages. An answer given to the user (a query, a research
answer) cites pages as panel links instead — `scripts/wiki panel-link <projects-relative path>`
returns `/project/<p>/wiki?file=…` for a wiki page and `/view/…` for any other file, the same
route the panel's wikilink renderer builds. Origin-relative: never a host or port, never a bare
path, never a hand-encoded URL.

Body wikilinks point only at pages that exist — the ones `wiki/entities/index.md` and
`wiki/concepts/index.md` list, the source pages being cited, and records. A name with no page yet
stays plain text in the body; listing it in the frontmatter `entities:` / `concepts:` is what
counts it toward its page. A link to a page that does not exist is a `broken` lint finding, not a
placeholder.

Frontmatter paths: `sources:` and `cited:` entries are project-root paths with `.md`
(`wiki/sources/<kind>-<stem>.md`) so lint resolves them; `record:` and `raw:` are project-relative
paths with `.md`. A YAML list item that starts with `[[` must be quoted (`- "[[wiki/…]]"`).

## No code identifiers outside `repos/`

`entities/` and `concepts/` describe the domain: what a thing is, why it is so, what broke and why,
who decided. They never name files, paths, functions, classes, components, flags or env vars. Where
a concept is implemented, link the repo page: `see [[wiki/repos/pavilio/speech-relay]]`. Code-level
detail lives only under `wiki/repos/<repo>/`. `scripts/wiki lint` flags violations as
`codeIdentifiers`. A ```` ```mermaid ```` diagram is not a code block: lint does not report it as a
fence, but a file path inside it is still a violation (§ Diagrams).

## Diagrams

Concept, overview and repo pages may carry one or two ```` ```mermaid ```` diagrams where the
page describes a lifecycle, a decision rule, an ordering between actors or a map of how parts
relate — the angles prose spreads over several sections. Source, entity, question and note pages
carry none (a source page keeps a diagram its record already had).

- **A diagram summarises cited prose; it never carries a claim of its own.** Every node and edge
  restates something the page's text already says with a citation. Nothing inferred to make the
  picture complete.
- Pick the type by angle: `stateDiagram-v2` for a lifecycle, `flowchart TD` for a decision rule,
  `sequenceDiagram` for actor ordering, `flowchart LR` for a map. Under ~25 nodes.
- Labels in quotes — `id["…"]`, `-->|"…"|`; no em dash in a bare `subgraph` title. Domain words in
  labels, never code identifiers.
- On rewrite, keep an existing diagram and update it when its claims changed; drop it only when
  the prose it summarised is gone.
- `scripts/wiki lint` parses every diagram and reports failures as `diagrams` (page + line). A
  `diagramCheck: "unavailable: …"` means the parser could not load — nothing was checked.

## Reading ladder

The reading ladder is the fixed read order for any skill or query that needs project knowledge.
It is the budget, not a minimum — stop as soon as the question is answered.

1. `CONTEXT.md` — the glossary, always, whole.
2. `wiki/index.md` — sections only.
3. ≤2 section indexes, chosen by their one-line descriptions.
4. ≤3 pages, chosen by their index descriptions: knowledge pages before source pages. Open a
   record only when a source page points at it and the pages did not answer.
5. `wiki/repos/<repo>/` only when the question or task is about code — descend from the
   repository entity page (`repos/<repo>/index.md`, then ≤2 repo pages). Never for a general
   question.
6. A `<project>:` link to another project's wiki only when the page in hand does not answer —
   including the `[[knowledge:wiki/…]]` back-links under a source page's `## Knowledge`. When the
   target project is `kind: research` (`scripts/wiki project --name <p>` → `kind`), every claim
   taken from it is labelled `(research, unverified)` in the answer, unless the reader is itself
   a research project.

7. The shared `knowledge` wiki (`projects/knowledge/wiki/`: `index.md` → ≤2 section indexes → ≤2
   pages) when the topic is a tool, library, platform or technique rather than this project's own
   decisions, or when the project's wiki did not answer. Cite it as `knowledge:wiki/…`.

No `wiki/` → read `CONTEXT.md` whole, as before, then step 7 when it applies. Readers other than
`/pavilio-wiki` queries walk the ladder without logging, writing or taking the lock.
